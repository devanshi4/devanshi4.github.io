Case 1 · Entity resolution In progress · built module by module

Which records are the same cell tower?

Telecom Entity Resolution & Iceberg Lab · Spark SQL · Apache Iceberg · AWS S3 · EMR Serverless · Glue

CSV · JSON · Parquetbronze: raw as deliveredsilver: standardize + matchgold: canonical sites + crosswalkIceberg on S3
Problem

Network inventory, RF planning and field operations describe the same cell sites with no shared ID. Names are abbreviated, addresses misspelled, coordinates rounded.

Approach

Profile each source's grain, standardize, then match on evidence: house number, ZIP and distance. Inventory bridges the other two. Ambiguous records go to review instead of being guessed.

Result

78 source records resolve to 24 canonical sites, with a crosswalk back to every source ID, scored against a hand-built answer key.

Decisions and trade-offs
  • Synthetic data with an answer key. Because the true site for every record is known, precision and recall are measured, not eyeballed.
  • Profile before matching. Each source has a different grain (per site, per plan version, per work order), so joining them directly would multiply rows.
  • Inventory is the bridge. RF planning and field ops share only a free-text name, so they link through inventory, the one source with both coordinates and an address.
  • Ambiguity goes to review. A work order with no house number could belong to two towers. The pipeline flags it rather than guessing.
  • Explicit survivorship rules. When field ops reports an equipment swap newer than inventory, the newer, more specific source wins.

Case 2 · Spark performance

Spark Performance Lab

PySpark 4.0 · Spark UI · History Server · multi-executor cluster

skewed join (baseline)diagnose in Spark UIAQE skew joinsalted joinaggregate before joinverify + compare
Problem

One merchant owns 21 of 30 million rows. In the baseline join, one task read 310 MB and ran 12.7 s while the median task took half a second.

Approach

Reproduce it on a real cluster, then compare three fixes: AQE skew join, salting, and aggregating before the join. Each must return the same 7,200-row report.

Result

Aggregating first made the join stage 5× faster and removed all disk spill. Total job time fell from 23 s to 17 s.

Decisions and trade-offs
  • Changing the query beat tuning Spark. Aggregating before the join removed the spill entirely; configuration alone (AQE) helped less.
  • Balanced isn't the same as fast. Salting evened out task sizes but added as much work as it saved, so I rejected it for this workload.
  • Correctness first. Every fix is checked against the baseline's 7,200-row report before its timing counts.

Case 3 · Streaming

Market Pulse

Postgres · Debezium · Kafka · Apache Iceberg · GCS · BigQuery · dbt · Dagster · Docker

Postgres WALDebezium CDCKafkamicro-batch writerIceberg (bronze)dbt silver/goldBigQuery
Problem

Stream trades from a simulated brokerage, a trade every 3 s and prices every 60 s, into portfolio analytics without losing or double-counting a trade.

Approach

Debezium reads the Postgres write-ahead log. Kafka offsets commit only after a successful Iceberg write; dbt deduplicates and builds P&L, moving averages and account rankings.

Result

No lost or double-counted trades, and every row carries its topic, partition, offset and CDC operation for debugging.

Decisions and trade-offs
  • CDC instead of app-published events. Reading the WAL means the stream can never drift from the database.
  • At-least-once, then dedupe. Committing offsets after the write means a crash can replay but never lose data; dbt removes the duplicates.
  • Dagster for orchestration. Asset-based runs make the tested model refreshes and bronze health checks visible in one place.

Case 4 · Lakehouse on AWS

E-commerce Lakehouse

Kinesis · Lambda · S3 · PySpark · AWS Glue · Athena · Airflow · IAM

KinesisLambdaS3 bronzePySpark silverPySpark goldGlue CatalogAthena
Problem

Clickstream events arrive continuously (about 5 per second) while orders arrive in a daily batch. Both need to land in one queryable model.

Approach

Event-driven Lambda for streaming, a scheduled Airflow DAG for batch, PySpark through bronze, silver and gold layers on S3, cataloged in Glue.

Result

5 gold tables queryable in Athena, with date partitions that keep scans and cost small.

Decisions and trade-offs
  • Both ingestion patterns in one platform, so the same medallion layers serve real-time and batch data.
  • Hive-style date partitions keep Athena scans, and cost, proportional to the dates queried.
  • Least-privilege IAM with separate roles for Lambda and Glue.

A pipeline that crashes pages someone in five minutes. Wrong data that looks fine can sit in a report for days. So I put tests between layers, validation where data enters, and loads that can re-run without creating duplicates.
