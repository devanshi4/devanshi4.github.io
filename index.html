About me

The most dangerous data failure isn't a crash

A pipeline that crashes pages someone in five minutes. Wrong data that looks fine can sit in a report for days. Most of what I build exists to catch exactly that.

I'm a data engineer at Cloudify Technologies, a consultancy that embeds me on client data teams. For a Fortune 500 telecom provider I own production dbt models on Snowflake. For a global payments platform I built the data models and Spark pipelines behind risk analysis and fraud detection.

Most of my favorite work starts with numbers that don't agree. Two reports show different totals, a fifth of the projects have no site attached, or a 400-line SQL rule quietly double-counts errors. I trace the problem back to its source, fix it there, and add the check that stops it from coming back.

I started out as a data analyst at USC, which is why I think about the people reading the dashboard, not just the pipeline feeding it.

Outside work I build end-to-end pipelines to go deeper on the tools: streaming with Kafka and CDC, lakehouses on S3 and Iceberg, and Spark tuning I can measure in the Spark UI.

Telecom Entity Resolution & Iceberg Lab

Three systems describe the same cell sites: network inventory, RF planning and field operations. They share no common ID. Names are abbreviated, addresses misspelled, coordinates rounded. This project works out which records describe the same physical site, builds one canonical table with a crosswalk back to every source ID, and maintains it with Spark SQL and Iceberg, first locally and then on AWS.

The data is synthetic. Real network data can't be shared, so I hand-built three source files that mimic the problems I see at work. Every record tests a specific edge case, and an answer key records which site each one truly belongs to, so match quality can be scored instead of eyeballed.

Architecture

CSV · JSON · Parquet→ Bronze: raw as delivered→ Silver: standardize + match→ Gold: canonical sites + crosswalk→ Iceberg on S3 · EMR Serverless · Glue
  • Profile before matching. Each source has a different grain: one row per site, per plan version, or per work order.
  • Inventory is the bridge. RF planning and field ops share only a free-text name, so they link through inventory, the one source with both coordinates and an address.

Decisions so far

  • Synthetic data with an answer key. Because the true site for every record is known, precision and recall can be measured, not guessed.
  • Ambiguity goes to review. A work order with no house number could belong to two towers. The pipeline flags it instead of guessing.
  • Conflicts follow explicit survivorship rules. When field ops reports an equipment swap newer than inventory, the newer, more specific source wins.

Market Pulse

Streaming · GCP

A real-time pipeline for a simulated stock brokerage. Trades are captured from Postgres with change data capture, streamed through Kafka with live market prices, landed as Iceberg tables, and modeled into portfolio analytics.

Trade every 3 sPrices every 60 sAt-least-once delivery
PostgresDebeziumKafkaIcebergGCSBigQuerydbtDagsterDocker
Architecture & decisions
Postgres WAL→Debezium CDC→Kafka→Micro-batch writer→Iceberg (bronze)→dbt silver/gold→BigQuery
  • CDC instead of app-published events. Debezium reads the write-ahead log, so the stream can never drift from the database.
  • Offsets committed only after a successful write. A crash never loses data; duplicates are removed downstream.
  • Lineage on every row. Topic, partition, offset and CDC operation travel with the data for debugging.

Weather Data Platform

Batch ELT · AWS

A scheduled Lambda pulls hourly weather for several cities into S3. Airflow loads it into Snowflake, and dbt turns it into a tested star schema.

Idempotent at every layerIncremental fact modelTests between layers
LambdaEventBridgeS3SnowflakedbtAirflowDocker
Architecture & decisions
Open-Meteo API→Lambda (daily)→S3 raw JSON→COPY INTO→Snowflake RAW→dbt star schema
  • Re-running never duplicates. Per-date S3 keys, COPY INTO file tracking and a QUALIFY dedupe all make retries safe.
  • Incremental processing. The fact table merges only rows past the watermark, so cost stays flat as history grows.
  • Raw kept immutable. The whole warehouse can be rebuilt from S3 if a transformation bug is found.
